## Enforcement

Three deterministic checks back this policy; none rely on an agent choosing to comply:

1. **Claude Code hook** (`.claude/settings.json` + `.claude/hooks/`): a `PreToolUse` hook blocks any `Write`/`Edit` under `apps/`, `packages/`, or `infra/` in a session until a `PostToolUse` hook has recorded that `progress.md` was read in that same session. Enforces "read before writing any code" for AI agents using Claude Code specifically.
2. **Git pre-commit hook** (`.githooks/pre-commit`, activated via `git config core.hooksPath .githooks` — run once per clone, e.g. `make hooks-install`): blocks any commit that stages changes under `apps/`, `packages/`, or `infra/` unless `progress.md` is staged in the same commit. Enforces "update after completing work" for any committer (human or agent), regardless of tool. Escape hatch: `git commit --no-verify` for changes that genuinely don't warrant a progress.md update.
3. **CI check** (`.github/workflows/ci.yml`, job `progress-tracker`): re-runs the same check against the PR diff. Catches the case where hooks aren't installed locally or `--no-verify` was used — nothing merges without it passing.

### Phase 1 — E1 Auth & Organizations, E2 Inference wiring, E3 Chat streaming, E4 History & Search
Full vertical slice: sign up → land in an isolated org → chat (streaming, with fallback) → conversation persists and is searchable. Implemented per a plan the user approved (`AskUserQuestion`/`ExitPlanMode` not needed here — this was researched and planned solo, then approved), sequenced E1 backend → E1 frontend → E2 → E3 → E4 → full-stack verification. Real Postgres/Redis throughout (this is the first Phase 1 work done against a live DB, not offline checks).

- [x] **E1 backend — auth & orgs** (`apps/api/src/afridock_api/{auth/,api/routes/{auth,organizations}.py,db/models/{user,organization}.py}`, migration `0002`): fastapi-users v13 with cookie+JWT transport (matches the frontend's existing `credentials: "include"` everywhere — zero fetch-layer changes needed); `User` extends fastapi-users' base with `org_id`/`role`/`display_name`; signup (`UserManager.create` override) always creates a brand-new `Organization` and makes the user its Admin; email verification required to log in (`requires_verification=True`) with the link **logged via structlog**, not emailed (no SMTP provider in the stack yet — `UserManager.on_after_register`/`on_after_forgot_password`); org member invite/list/update-role/remove endpoints reuse fastapi-users' reset-password flow for invite completion instead of a bespoke invite-token system.
- [x] **RLS bypass bug found and fixed**: migration `0001`'s RLS policies were silent no-ops — Postgres superusers *and* table owners always bypass RLS regardless of ENABLE/FORCE, and the API connected (and ran migrations) as `afridock`, the superuser `docker-compose` creates. Migration `0002` creates a non-superuser `afridock_app` role for the running API to connect as (`config.py`'s `database_url` vs `migrations_database_url` split); `FORCE ROW LEVEL SECURITY` added everywhere as defense-in-depth. **Two follow-on RLS bugs found while proving this end-to-end**, both fixed in the same migration: (1) the `users`/`organizations` tables need a "pass through when no org context is set yet" carve-out for login/signup itself (chicken-and-egg: can't look up a user by email, or insert a brand-new org, if RLS demands an org context that doesn't exist yet) — but pooled connections reset a touched custom GUC to `''`, not `NULL`, so the carve-out had to check `coalesce(current_setting(...), '') = ''`, not `IS NULL`; (2) that `OR`-based carve-out could still error, since Postgres doesn't guarantee `OR` short-circuits — the `::uuid` cast on the right side ran anyway on `''` — fixed with a `CASE WHEN ... THEN true ELSE ... END` (which *does* guarantee single-branch evaluation) instead. Proven correct via a raw-SQL test connecting *as* `afridock_app` directly (bypassing the app layer entirely) scoped to each org in turn.
- [x] **Alembic revision-id bug found and fixed**: the original descriptive revision strings (`"0001_conversations_messages_providers"`, 38 chars) overflowed Alembic's default `alembic_version.version_num VARCHAR(32)` column on the first-ever live migration run. Both migrations' `revision`/`down_revision` shortened to `"0001"`/`"0002"`; filenames stay descriptive.
- [x] **E2 — inference stub-fallback** (`inference/client.py`): `.env.example` already said "leave blank for local stub mode" — made that literal. `InferenceClient` checks whether any profile in the resolved chain has its provider's credential configured (`huggingface_api_token`/`openai_api_key`/`anthropic_api_key`, now `config.py` settings); if none do, it serves a canned, incrementally-streamed stub completion instead of raising `NoAvailableModelError` — the whole chat pipeline is demoable with zero secrets, and graduates to real inference the moment a key is set, no code changes. `stream()` extended to loop fallback candidates the same way `complete()` already did (falls back on a pre-first-token error only; mid-stream fallback stays out of scope per the existing docstring).
- [x] **E3 — chat streaming endpoint + persistence** (`api/routes/conversations.py`): `POST /conversations` (create), `GET /conversations/{id}/messages` (history), `POST /conversations/{id}/messages` (SSE, matches `useChatStream`'s existing `message`/`message_end`/`error` event contract exactly). **Real bug found via Playwright, not curl**: the assistant's reply was only persisted *after* the whole SSE generator completed — a client disconnecting mid-stream (navigating away) silently lost it. Fixed with a `finally` block... which itself needed a second fix: `SlowAPIMiddleware` is a Starlette `BaseHTTPMiddleware`, which runs the whole request in an anyio task group that cancels its scope on client disconnect — including new awaits inside that `finally` block — so the persistence call is now wrapped in `anyio.CancelScope(shield=True)` to survive it. Also: `send_message` deliberately does *not* use `Depends(get_org_session)` — FastAPI tears down `yield`-dependencies as soon as the handler *returns* the `StreamingResponse` object, before the body actually streams, so a dependency-injected session would already be closed by the time the generator runs; it uses a new `db/session.py:org_scoped_transaction` (a plain `@asynccontextmanager`) directly instead, opening short-lived transactions before and after streaming.
- [x] **E4 — conversation list + full-text search**: `GET /conversations?q=` (Postgres `plainto_tsquery`/`ts_rank` against the existing `search_tsv` trigger from migration `0001`). Personal history (scoped to `org_id` **and** `user_id`, not team-shared) — a deliberate reading of "conversations persist... their previous conversations are listed" as personal, ChatGPT-style history, satisfying "scoped to the user's org" a fortiori.
- [x] **E1 frontend — real auth**: `services/auth.ts` (login is form-urlencoded per fastapi-users' `OAuth2PasswordRequestForm`, not JSON like everything else), `store/authStore.ts` rewritten to hold the real session (populated via `hooks/useAuthBootstrap.ts` calling `GET /users/me`) instead of the hardcoded `"admin"` placeholder, `routes/{Login,Signup}Page.tsx`, `components/auth/AuthGuard.tsx`. Redirects use `window.location.href` (hard navigation), not `<Navigate>`/`useNavigate` — consistent with this router's existing jsdom/AbortSignal workaround (avoids client-side navigation firing on mount entirely).
- [x] **E3 frontend — real routing**: `/chat` creates a conversation (`useCreateConversation`) and hard-redirects to `/chat/:conversationId`; `ChatPanel` loads persisted history (`useConversationMessages`) into `chatStore` once per conversation (guarded by a ref, not just the query result, so a background refetch can't wipe out messages already streamed in since); `ConversationsPage` links to `/chat/:id` instead of a shared `/chat`.
- [x] **Real bugs found by the test suites (not just manual testing)**: `Sidebar.tsx`'s `user?.email.slice(...)` crashed on a null user — `?.` only makes the immediately-following access optional, not the rest of the chain; fixed to `user?.email?.slice(...)`. `LoginPage`/`SignupPage`'s `<label>`s weren't associated with their `<input>`s (no matching `htmlFor`/`id`) — an accessibility bug caught because Playwright's `getByLabel` (which mirrors the accessible-name computation screen readers use) couldn't find them either.

**Testing**: 25 new backend pytest tests (`tests/test_{auth_signup,tenant_isolation,chat_flow,organizations_rbac,inference_stub}.py`) against the live Postgres via `docker compose run --rm api pytest` — real RLS, real migrations, no mocked DB layer. A shared `event_loop` fixture (session-scoped) was needed in `conftest.py`: pytest-asyncio's default per-test event loop conflicts with `db/session.py`'s module-level asyncpg engine, created once at import time bound to whichever loop is running then. Full Playwright browser run (signup → verify-link → login → send message → stub response streams in → appears in conversations list → search matches/doesn't-match correctly → logout), zero console errors. `make test`/`make lint` clean across both apps throughout.
